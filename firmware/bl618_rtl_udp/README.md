# BL618 固件：RTL-SDR → Wi-Fi → iPhone

怎么买、怎么接、怎么编译烧录、怎么连 Wi-Fi，见[仓库首页](../../README.zh-CN.md)（[English](../../README.md)）。这份记的是实现细节、实测数据和协议格式。

一块安信可 **Ai-M61-32S-Kit**（BL618，Wi-Fi 6 + 4 MB PSRAM）同时当 USB 主机和 Wi-Fi 网卡：
RTL-SDR 插在模组的高速 USB 上，板子在 Wi-Fi 上提供原样的 `rtl_tcp`。iPhone 上支持 `rtl_tcp` 的 App 直接填板子的地址就能连。
同时在 1235 端口提供 `rtl_udp`（见下文），给愿意多实现一点协议、想精确知道丢了什么的客户端用。

```
RTL-SDR ──USB 2.0 高速──▶ BL618 ──Wi-Fi──▶ iPhone 上的 rtl_tcp App
                         ├ CherryUSB 主机 + librtlsdr（和 Teensy 用的是同一份）
                         ├ 4 MB PSRAM：程序代码 1.1 MB（开机从 flash 拷来）+ 1 MB 保护区 + 1.75 MB 环形缓冲，扛 Wi-Fi 的抖动
                         ├ lwIP TCP，端口 1234：rtl_tcp
                         └ 端口 1235：rtl_udp（命令 TCP，采样 UDP）
```

1234 上的协议还是 TCP，只是 TCP 下面从网线换成了 Wi-Fi。

## 状态

**2026-10-30 第一次上板子，两半都实测过。** 插上 RTL-SDR，经 rtl_udp 收 101.7 MHz 调频：立体声导频 28–29 dB、
立体声 100%，和同一根 RTL-SDR 直插电脑时（32–34 dB）相当；客户端 App 在 2.4 MSPS 下收台，扬声器出声。

- 插 RTL-SDR、用 RTL2832U 自己的计数器测（rtl_udp，30 秒）：1.024 / 2.0 / 2.4 MSPS 网络零丢包、内容全对；
  空口一时变慢超过环形缓冲扛得住的长度（2.4 MSPS 下 0.44 秒）时，板子丢 1–4%，丢在哪里如实报告。
- **USB 控制传输的长度要减掉 SETUP 的 8 字节。** CherryUSB 的 EHCI 把三段 qTD 的长度加在一起，4 字节的读报成 12，
  librtlsdr 的 `r82xx_read` 因此每次都判失败（`i2c rd failed=12 len=4`），R820T 只设了一半，收到的只有噪声；
  计数器测试照样通过，因为测试模式绕过调谐器。`rtl_usb.c` 里修正。

- 不插 SDR、用板子自己的计数器测（rtl_udp，内容逐包校验）：**2.0 和 2.4 MSPS 零丢失**（摆放好的时候）。
- **摆放影响很大**：杜邦线和手离板子的天线近时，同一块板子的 iperf UDP 从 50 掉到 18 Mbit/s。测之前把线拉开、手拿走；
  电脑刚连上热点的十几秒里 macOS 会在后台扫描别的信道，也要等它过去。
- **程序代码从 PSRAM 执行，不从 flash 执行。** 从 flash 执行时，Wi-Fi 驱动的发送路径装不进 32 KB 的指令缓存，
  每发一个包 `udp_sendto` 要约 420 µs 的 CPU，CPU 跑满也只有约 1.4 MSPS；开机把代码拷进 PSRAM 后降到约 100 µs。
  详见下文“rtl_udp”。
- 上板后修掉的三个问题：Wi-Fi 事件回调里调用了会等待的函数（热点一起来就死机）；拔 dongle 时控制传输可能用到
  CherryUSB 刚删掉的锁；lwIP 堆从 64 KB 加到 80 KB（发送时每秒分配失败约 600 次）。
- 状态行每 5 秒打印三个堆的剩余量（`free KiB ocram … wram … psram …`）。热点模式下 OCRAM 只剩约 20 KB，
  WRAM 约 2 KB：**SRAM 已经没有余量**，再加东西要先看这几个数。

编译：XuanTie GCC v2.6.1，SDK 版本固定（见 `tools/fetch-deps.sh`），我们自己的代码零警告。代码（`CONFIG_PSRAM_COPY_CODE`）
和 1.75 MB 环形缓冲（前面是 1 MB 保护区，见下文"PSRAM 里被 Wi-Fi 写坏的一个字"）在 PSRAM，96 KB USB 暂存缓冲在不经缓存的 SRAM 别名区。

## 编译

命令见[仓库首页](../../README.zh-CN.md#编译)。这里是背景和开发时用的工具。

在 x86_64 Linux 上编（验证过的是 CentOS Stream 9）。
工具链来自博流官方的 [toolchain Release](https://github.com/bouffalolab/toolchain/releases/tag/default)：

  生成的 LTO 中间代码，v2.10.2 的 GCC 10.4 链接时直接拒绝（`LTO version 9.0 instead of the expected 9.4`）。
  2026-10-27 在 Ubuntu 24.04 容器里实测：我们自己的代码用 v2.10.2 能编过，链接这一步过不去。
  （v2.10.2 另外还需要 glibc 2.36，CentOS 9 只有 2.34。）
- 那里的 macOS 版只有 arm64，只能在 Apple 芯片的 Mac 上用；Intel Mac 用不了。

在 Mac 上改代码时，`firmware/tools/build-all.sh` 会把代码同步到编译机、编好，同时编 Teensy 那一块。
编译机是 `ssh` 能直接登录的名字，写在 `firmware/tools/build-host`（一行，不提交），或者用环境变量
`BL618_HOST=...`；`flash-bl618.sh` 也从这里取。

板型用 SDK 的 `bl616dk`：安信可自己的 Ai-M6X SDK（`gitee.com/Ai-Thinker-Open/aithinker_Ai-M6X_SDK`）给
Ai-M61 用的也是它，40 MHz 晶振、UART0 在 GPIO21/22、PSRAM 初始化都和博流 SDK 的一致（2026-10-27 对过）。
模组是 8 MB Flash，`bl616dk` 默认只映射前 4 MB，固件 1.1 MB，不受影响。

只想在 Mac 上检查代码有没有写错：`firmware/tools/check-bl618.sh`（需要 `brew install llvm`）。

## 烧录

步骤见[仓库首页](../../README.zh-CN.md#烧录)。细节：

- 写入位置来自 SDK 按分区表生成的 `flash_prog_cfg.ini`：boot2 在 `0x0`，分区表在 `0xE000`，固件在 `0x10000`。
  `erase = 1` 只擦要写的几段，所以存热点密码的 PSM 分区（`0x3E9000`）不受影响；用 DevCube 做整片擦除才会清掉它。
- 波特率 500 kbit/s：板载是 CH340C，SDK 说它烧录最多 500 kbit/s。换了 CP2102 或 FT232 的板子可以设 `BL618_BAUD=2000000`。
- 烧录工具默认先压缩再写，板子解压完要在 30 秒内回确认；500 kbit/s 下 1.1 MB 的固件偶尔赶不上，卡在写入那一步。
  把 `eflash_loader_cfg.ini` 的 `decompress_write` 改成 `false` 就不压缩了（2026-11-02 在这块板子上遇到）。
- 这块板子没有自动下载电路（原理图上那部分是 NC），每次都要手按 IO2 + EN。

串口日志 2,000,000 波特率。

## Wi-Fi

热点名和密码怎么拿、怎么改密码、怎么连手机热点，见[仓库首页](../../README.zh-CN.md#第一次开机拿到-wi-fi-名字和密码)。实现上的细节：

- 密码在第一次开机时由芯片的硬件随机数生成，12 位，去掉了 0/o、1/l/i 这些容易看错的字符，存在 Flash 的 PSM 分区。
  `bridge_ap_newkey` 只是把它删掉，下次开机重新生成。
- 填了 `BRIDGE_STA_SSID` 时，20 秒连不上就退回去开自己的热点。
- **`rtlsdr.local`（mDNS）**：两种模式都会广播，还登记了 `_rtl_tcp._tcp` 服务。Teensy 版用的也是 `rtlsdr`，
  所以 App 里填 `rtlsdr.local` 不用管用的是哪块板子。两块同时在一个网络里，后上线的那块会改用
  `rtlsdr-2.local`，串口日志里会写。
- 连上别人的网络后，板子会关掉 Wi-Fi 省电模式。

## 指示灯

每个灯是什么意思见[仓库首页](../../README.zh-CN.md#指示灯)。实现上的细节：

- 三个灯：左边的 RGB 灯（规格书图 5 的①，红 IO12、绿 IO14、蓝 IO15），右边 IO27、IO29 旁边两个单色灯
  （原理图的 LED5 “W” 和 LED4 “C”，规格书的表里没写；实物上 W 是黄灯、C 是白灯）。
- **USB 传输报错不等于丢了数据。** 推流时大约每 100 次 32 KB 的传输有一次以 `-USB_ERR_IO`（12）结束，
  但实测这些传输的数据**全都完整收到了**：一分钟 12 次，Mac 端用 RTL-SDR 的测试计数器逐字节核对，没有一个字节不对。
  旧版本把它们整块扔掉，悄悄丢了约 1.4% 的样本，而且没有报告给客户端；现在照常交出，不算故障，黄灯也不为它闪。
  状态行里的 `usb transfers failed: N after arriving whole, N partly, N empty` 就是这三类的计数，只有 `empty` 才真的丢了东西。
  16 KB 一次传输时这种报错少得多（每 MB 0.13 次，32 KB 时是 0.43 次），更像是 EHCI 串联两个 qTD（一个 qTD 最多 20 KB）
  时的问题，不像是飞线：飞线出错应该和字节数成正比。
- 两种丢数据分开显示，一眼就知道该查板子还是查 Wi-Fi。到目前为止实测丢数据都是 Wi-Fi 那头（`udp_sendto` 被拒、
  每秒发出的包不够），所以拿着板子走，紫蓝闪的地方就是 Wi-Fi 不够用的地方。
- 出问题的闪法在最后一次出问题之后还保持 2 秒（中断是 3 秒），偶尔丢一块也看得见。
- 呼吸用的是硬件 PWM，只有蓝灯（IO15，PWM0 通道 3 负）和白灯（IO29，通道 2 负）能呼吸：红灯、绿灯和它们分别
  共用一个通道。绿灯不再使用。
- 快闪每秒 5 次，呼吸 3 秒一次。代码在 `led.c`。

## PSRAM 里被 Wi-Fi 写坏的一个字

**Wi-Fi 运行时，PSRAM 地址 `0xa8201300` 上的 4 个字节每隔 1 到 4 分钟会被写成 0**，板子空闲时也一样。
写它的东西不在我们的代码里，也不是 CPU：2026-11-03 逐项排除过，已报给博流（[bouffalo_sdk#272](https://github.com/bouffalolab/bouffalo_sdk/issues/272)）。

- **现象**：计数器测试里大约每 10 分钟有 4 个字节变成 0，前后的数据都完好，所以只有逐字节核对才看得出来。
  收台时就是偶尔两个采样变成 0，人耳听不出来。
- **排除过程**：换了五种内存布局，地址始终不变；固件里搜不到这个地址常量；硬件观察点（开机自检有效）没有触发，
  说明不是任务里的 CPU 写入；包住中断分发函数，每个中断前后这个字都没变；拔掉 RTL-SDR 照样发生；
  **不启动 Wi-Fi 就完全不发生**。所以最可能是 Wi-Fi 硬件的 DMA，在闭源库里，这里修不了。
- **规避**：`sample_ring.c` 在环形缓冲前面放了 1 MB 保护区盖住这个地址，环形缓冲因此从 2 MB 缩到 1.75 MB。
  开机日志会打 `ring guard covers 0xa8201300`；如果哪天代码大小变化让保护区盖不住了，这一行会变成 `MISSES`。
  状态行每分钟检查一次保护区，被写过就打印 `ring guard written: … +0x… = 0x00`，所以这个问题还在不在，看日志就知道。
- 修复后实测（2026-11-03）：rtl_udp 1.024 / 2.0 MSPS 各 60 秒、rtl_tcp 1.024 MSPS 30 秒、幅度格式 2.0 MSPS 30 秒，
  全部零丢失、内容全对。
- 查的过程中先后猜错了三次（扫描结果数组越界、USB 暂存缓冲、环形缓冲本身），每次都是被下一组数据推翻的；
  最后定位到地址，靠的是板子在发包前自己核对计数器，并打印出错字节的绝对地址。

## 代码结构

| 文件 | 作用 |
|---|---|
| `rtl_usb.c` | CherryUSB 类驱动：给 librtlsdr 的同步控制传输；批量 IN 端点一次挂一个 32 KB 传输，完成就在中断里挂下一个 |
| `libusb_shim.c` | librtlsdr 要的 libusb 接口，和 Teensy 版用同一个头文件 |
| `../common/librtlsdr/` | 原样的 librtlsdr，两个固件共用这一份，不复制 |
| `sample_ring.c` | PSRAM 里 1.75 MB 的环形缓冲和它前面的 1 MB 保护区：Wi-Fi 跟不上时整块丢弃并计数，I/Q 不会错位；还记下每个缺口在流里的位置，给 rtl_udp 用 |
| `rtl_tcp_server.c` | 拷贝任务（USB → PSRAM）和服务任务（rtl_tcp / rtl_udp 会话、命令、发样本、各种断开）；协议格式写在文件开头 |
| `led.c` | 三个指示灯，每 20 ms 看一次 Wi-Fi、RTL-SDR、会话和两种丢块计数；蓝灯和白灯的呼吸用 PWM |
| `wifi_link.c` | 连热点或自己开热点；连上后关掉 Wi-Fi 省电模式；在有地址的网络上广播 `rtlsdr.local` |
| `config/` | CherryUSB、lwIP、FreeRTOS 的配置，取自 SDK 的例子 |

## 和 Teensy 版不同的两处

1. **一个端点同时只能挂一个传输。** CherryUSB 的 EHCI 驱动给每个传输单独分配一个 QH，数据翻转位记在 QH 里，
   同一个端点挂两个传输，翻转位会互相打架，主控把好数据当重复包悄悄丢掉。所以一次只挂一个 32 KB 的传输
   （硬件连续跑两个 16 KB 的 qTD），两个传输交接时有一个很短的空档。**会不会丢数据要用计数器测试回答。**
   如果丢，就要自己写一个常驻 QH 加循环 qTD 链的流式驱动，USBHost_t36 和 Linux 都是这么做的。
2. **Wi-Fi 不像网线那样匀速**，重传、邻居的信标、手机省电都会让链路停几十到几百毫秒。所以 USB 和 TCP 之间加了
   PSRAM 里 1.75 MB 的缓冲：2.4 MSPS 下能扛 0.38 秒，1.024 MSPS 下 0.9 秒（原来是 3 MB，代码挪进 PSRAM 后让出了 1 MB，
   2026-11-03 又让出 0.25 MB 给保护区）。

## rtl_udp（端口 1235）

`rtl_tcp` 的命令不变，采样改用 UDP 发。为什么要它，以及它是什么样子：

- **丢失看得见，而且精确。** `rtl_tcp` 是无格式的字节流，板子丢了一块，客户端只能从 8 位计数器上猜；
  丢掉的正好是 256 字节的整数倍时（每块 USB 数据都是），计数器根本看不出来。rtl_udp 的每个包都带序号和
  第一个采样的编号：**序号断了是网络丢包，序号连续、编号跳了是板子自己丢的**（环形缓冲溢出），两种分开计数，
  客户端按编号补零，时间轴不会错位。
- **不会被重传拖住。** TCP 要把每一段数据留在 lwIP 堆里等确认，速率被“堆大小 ÷ 往返时间”卡住；
  UDP 的包发出去就释放。
- **格式**（写在 `rtl_tcp_server.c` 开头，全部大端）：
  - 控制，TCP 1235：板子先发 20 字节 `"RTLU"` + 调谐器类型 + 增益档数 + 会话号 + 版本；之后客户端发
    `rtl_tcp` 的 5 字节命令，外加 `0x40 START_UDP`（参数是客户端的 UDP 端口），收到它才开始发数据。
  - 数据，UDP 1235 → 客户端：20 字节头（`"RU"`、版本、标志、会话号、序号、第一个采样的编号 u64），
    后面最多 1452 字节 I/Q，正好一个以太网帧，不会分片。
  - 心跳，客户端 → UDP 1235：每 100 ms 8 字节（`"RU"`、版本、`0x80`、会话号），10 秒收不到就停
    （原来是 2 秒：板子满速发送时自己的接收会丢包，2.4 MSPS 零丢失的流跑了 33 秒就被它断开过）。
- 1234 和 1235 同时开着，但同一时间只服务一个客户端，哪个端口的新连接都会顶替旧的。
- **只发幅度（版本 2 起）。** 客户端在 `START_UDP` 之前发 `0x41 SET_FORMAT 1`，之后每个采样只发 1 个字节的幅度，
  数据包头的标志位 bit 0 置 1，最多 1452 个采样一包。给 ADS-B 用：它只解包络、不用相位，2 MSPS 的 I/Q 要
  约 32 Mbit/s，只发幅度约 16 Mbit/s。实际摆放下这块板子大约跑 20–25 Mbit/s，前者会丢一半，后者不会。
  - 编码：`r = sqrt((2I−255)² + (2Q−255)²)`，发 `round(255 × sqrt(r / 360.6))`，也就是开方压缩，弱信号那一段分得细。
    用 dump1090 自带的真实录音 `modes1.bin` 比过：不量化时解出的帧和 I/Q 完全一样（171 对 171）；线性编码少了一种报文；
    开方压缩 169 帧，**每一种报文都在，没有多出来的**，少的两帧是另外完整收到过的重复报文。
  - 板子上是一张 128×128 的表（放 PSRAM，16 KB），按 `|2I−255|`、`|2Q−255|` 查，每个采样一次读表，不开方。
    这张表和客户端按上式算出的值在全部 65536 种 I/Q 组合上逐项比过，完全一致。
  - 老固件（版本 1）不认识这条命令：客户端看到版本 1 就不发，照收 I/Q；每个包也自带标志位，客户端从不假设请求被执行了。

**实测（2026-10-30，板子开热点在信道 13，接收端 Mac 直连，蓝牙关闭，不插 SDR 用板子的计数器，每项 20 秒）：**

| | 代码从 flash 执行 | **代码从 PSRAM 执行（现在的配置）** |
|---|---|---|
| rtl_udp @1.024 MSPS | 1.011 MSPS，零丢失 | 1.012 MSPS，**零丢失** |
| rtl_udp @2.0 MSPS | 约 1.4 MSPS，其余溢出 | **1.975 MSPS，零丢失** |
| rtl_udp @2.4 MSPS | 1.0–1.4 MSPS | 2.29 MSPS（95.5%），板子丢 1.5% |
| 每秒发包数 | 约 2100 | 约 3400 |
| 每个包的 `udp_sendto` | 400–430 µs | 95–120 µs |
| 满载时 CPU 空闲 | 5–9% | 28–48% |

（代码从 flash 执行时，SDK 自带的 iperf 发 UDP 是 31.4 Mbit/s，rtl_tcp @2.0 MSPS 约 1.3 MSPS。）

几条读数时要知道的：

- **从 flash 执行慢在取指令。** 代码在外部 flash 上，CPU 通过 32 KB 的指令缓存取指令；Wi-Fi 驱动的发送路径
  比缓存大，每发一个包缓存都被冲掉一遍，所以一轮里第一个包和后面的包一样慢（缓存不是冷，是在来回打架）。
  开机把代码拷进 PSRAM（`CONFIG_PSRAM_COPY_CODE`）后，同样的代码快了约 4 倍。
- **找它花了两个错的猜测**：lwIP 堆太小（确实存在，堆从 64 加到 80 KB 换来约 15%）和“不聚合时一帧的空口时间”
  （每帧的空口时间恰好也是约 400 µs，但 CPU 占用是 93%，说明在算不是在等）。状态行里每 5 秒有各任务的
  CPU 占比（`cpu: serve … IDLE … wifi fw …`）和发送分段计时，**下一个瓶颈先看这两行再猜**。
- **接收端 Mac 的蓝牙会让 2.4 GHz 吞吐掉一半。** 同一块板子、同一个信道：蓝牙开着（连着鼠标键盘），
  UDP 15 Mbit/s、ping 44 ms；关掉后 29 Mbit/s、ping 9 ms。测的时候关掉蓝牙，或者让板子连路由器、
  电脑走 5 GHz。手机同样有这个问题，戴着蓝牙耳机时要预期吞吐变低。
- 拥挤的信道不是主要原因：换到没有别的网络的信道 13，结果没有变好。
- 发送用的是 lwIP 的 raw UDP 接口（和 SDK 的 iperf 一样），不是 socket：socket 版只有 18.7 Mbit/s。
  另外因为开了 `HIGH_PERFORMANCE_PBUF`，socket 的 `sendto` 默认**不拷贝**调用者的缓冲区，所以 lwIP 配置里
  打开了 `LWIP_TCPIP_FORCE_TX_COPY`。

## 测试顺序

分三个阶段，每一步只多一个变量。前一阶段不过，就不进下一阶段：后面出了问题，就能知道是新加进来的那部分造成的。

### 第一阶段：不接 SDR，只看板子和 Wi-Fi

**先想好电脑怎么上网。** 电脑的 Wi-Fi 加入板子的热点后，就上不了网，也连不上编译机。两种办法：

- **电脑走有线网**（USB 网卡插网线），Wi-Fi 腾出来专门连板子。测的就是实际用法：设备直连板子，不经过路由器。
  连上后用 `route -n get default` 确认默认路由还在有线网卡上；板子的 DHCP 也会给一个网关，Wi-Fi 在服务顺序里排得更前的话，
  默认路由会被抢走。
- **板子连家里的路由器**：`wifi_secrets.h` 里填路由器 **2.4 GHz** 的名字和密码（BL618 只有 2.4 GHz），电脑留在原来的网络上，
  板子的地址看串口里 `got ip` 那一行。方便，但路径里多了一个路由器，测出来的数不完全等于直连。

**串口和烧录抢同一个口。** 烧录前关掉 tio，烧完再打开。CH340C 在 macOS 上一般是 `/dev/tty.usbserial-*` 或
`/dev/tty.wchusbserial-*`：插板子前后各 `ls /dev/tty.*` 一次，多出来的那个就是。

**热点名和密码只在串口里**：先打开 tio，再按 `EN`，开机那行 `[wifi] network "SDR-Bridge-XXXX" up, password …` 就是。

1. **烧录 + 串口**：`tio -b 2000000 /dev/tty.usbserial-xxx`，按 `EN` 复位，看到 `bl618_rtl_udp: RTL-SDR over Wi-Fi`。
   每 5 秒会有一行状态，此时应该是 `dongle absent, idle`。
2. **Wi-Fi 起来**：看到 `network "SDR-Bridge-XXXX" up, password …`（或者连热点时的 `got ip …`）。
   Mac 用这一行里的名字和密码连上（`networksetup -setairportnetwork en0 <热点名> <密码>` 也行），`ping 192.168.7.1` 能通，`ping rtlsdr.local` 也通的话说明 mDNS 正常。
3. **Wi-Fi 原始吞吐（iperf）**：只测无线电本身，我们的代码都不在路径上。
   Mac 上 `brew install iperf`（iperf2，和板子上的 iperf 用同一个协议，默认端口 5001），然后：
   ```bash
   iperf -s -i 1                               # Mac：当服务器，收
   ```
   ```
   iperf -c <Mac 的地址> -t 30 -i 1             # 板子串口里敲：板子发，方向和采样流一样
   ```
   Mac 的地址看 `ipconfig getifaddr en0`（连板子热点时是 `192.168.7.x`）。
   **要 38.4 Mbit/s 以上才能跑 2.4 MSPS**，32 Mbit/s 以上才能跑 2 MSPS 的 ADS-B，20 Mbit/s 以下这条路就停。
   只测板子发这个方向的话，Mac 上不需要真正的 iperf：板子的 iperf 客户端只管往外发，Mac 上开一个只收不回、
   统计字节数的 TCP 或 UDP 接收端就够了（2026-10-30 就是这么测的）。UDP 用 `iperf -u -b 60M -c <Mac 的地址>`，
   板子自己报的数是交给驱动的量，**以接收端统计的为准**。
   **测之前关掉 Mac 的蓝牙**，见上文“rtl_udp”里的实测。
4. **我们自己的网络这一半（合成计数器）**：板子没插 SDR 时，客户端打开测试模式，板子就在本地生成和 RTL2832U
   测试模式一样的递增计数器，按请求的采样率经过同一个环形缓冲和同一个发送循环发出去：
   ```bash
   firmware/tools/rtl_tcp_counter.py 192.168.7.1 --rate 1.024M --seconds 60   # 再试 2.0M、2.4M
   ```
   脚本会先说 `no dongle on the board`，最后一行要是 `PASS … (board's own counter, no USB)`。
   iperf 过了而这一步不过，问题就在 lwIP 配置或我们的发送循环，不在无线电本身。
   加 `--udp` 就改测 rtl_udp：每个包的内容按它自己的采样编号逐字节核对，网络丢包和板子丢的分开统计，
   比 TCP 模式的计数器严格得多（TCP 模式看不出整块丢掉的情况，只能看送达速率）。
   别的客户端（真正的 App）不会打开测试模式，板子 3 秒内就会断开它，所以不会有 App 把计数器当信号解调。

### 第二阶段：接上 SDR，只看 USB

5. **识别**：插上 RTL-SDR，串口看到 `RTL2832U 0bda:2838 claimed` 和 `dongle ready: …, tuner 6`（V4 是 R828D），
   状态行变成 `dongle open`。不识别或者反复断开，先量 `5V` 排针的电压（见上面“接线”）。
6. **计数器测试，判断 USB 丢不丢数据的唯一依据**：命令和第 4 步一样，这次计数器来自 RTL2832U 本身，
   脚本不会再提示 `no dongle`：
   ```bash
   firmware/tools/rtl_tcp_counter.py 192.168.7.1 --rate 1.024M --seconds 60   # 再试 2.0M、2.4M
   ```
   要求 0 断档、实际速率接近请求的速率。第 4 步在同一个速率下已经过了，这里再出断档就是 USB 这一半的问题：
   看状态行里 USB 端的 `dropped`（暂存缓冲没被及时取走）和 `bulk errors`。USB 端丢说明一个传输一个空档不够，
   见上面“和 Teensy 版不同的两处”第 1 条。

### 第三阶段：SDR 经过 Wi-Fi 到客户端，验证 rtl_tcp 的正确性

7. **长时间计数器测试**：2.4 MSPS 跑 10 分钟（`--seconds 600`），同时看状态行里 `ring … (peak …)`：
   峰值接近 2048 KiB 说明 Wi-Fi 的停顿快要超过缓冲扛得住的长度。
8. **真实信号**：电脑上任何支持 `rtl_tcp` 的软件（SDR++、GQRX 等）连 `192.168.7.1:1234`，听一个广播台。
   调频、改采样率、改增益都要能生效，串口里会打出每条命令（`cmd 0x01 …`）。
9. **iPhone**：连上 `SDR-Bridge-XXXX`（密码看串口日志），App 里填 `rtlsdr.local`。不通就填 `192.168.7.1`：IP 通、名字不通，
   说明是 Wi-Fi 驱动没收组播（mDNS），不是别的问题。断开再连、App 切到后台再回来，板子都要能接受新连接。
